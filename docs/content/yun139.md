# Yun139

[Yun139](https://yun.139.com) is the personal cloud storage service offered by
China Mobile (中国移动), also marketed as "MCloud" or "和彩云". It offers a
personal (个人云), a family (家庭云) and a shared-group (共享群) space with
web, mobile and PC clients.

Rclone accesses Yun139 through the same "personal_new" and family
orchestration APIs used by
[OpenList](https://github.com/OpenListTeam/OpenList). You need an
authorization token to configure the backend.

## Configuration

Run `rclone config` and follow the interactive setup; the backend
appears as `yun139` in the storage-type menu. The only required option
is the authorization token; the rest have sensible defaults.

### Obtaining an authorization token

The easiest way is to copy the `Authorization` header value from an
existing [OpenList](https://github.com/OpenListTeam/OpenList) 139 storage
config — the field is already a `Basic ` + base64 string.

Alternatively, log in to <https://yun.139.com> in a browser, open the
network panel, look for any request to `*.yun.139.com` and copy the
value of the `Authorization` request header. The value starts with
`Basic ` followed by the base64 of
`pc:<phone-number>:<token>|...|<expiry-millis>`.

### SHA-256 rapid upload (秒传)

Rclone masquerades as the official 139 PC client on every request to
the personal cloud. This is required for the server to honour the
`sha256` field in `/file/create` and short-circuit the upload to a
hash match (秒传). The masquerade is automatic and not
user-configurable.

### Family cloud (新家庭云)

The family cloud uses a different base host and a `family_id` (also
called "cloudID" or "群组 ID" in the 139 client). When your account has
exactly one family cloud the backend auto-discovers the id for you; if
you belong to several, you must set `family_id` to choose one — the
backend refuses to guess rather than pick the wrong group.

To find your `family_id`:

1. Open the 139 PC client and sign in
2. Click "我的家" (My Family) in the sidebar - the URL in the
   browser bar contains the id, e.g. `https://yun.139.com/family/12345678901234567`
3. Copy the trailing number

Then configure the backend:

```console
[myfamily]
type = yun139
authorization = ...
space = family
family_id = 12345678901234567
```

Without `family_id` the first family endpoint call returns
`1010220314: 家庭云不存在` - this is the live server's response, not a
backend bug. If the user account has not joined or created a family
group the family API has nothing to talk to.

### Shared group (共享群)

A shared group is a third space, separate from the family cloud: same host as
the family API, different namespace (`/hcy/mutual/adapter/isbo/openApi`) and
keyed on a numeric `group_id` (the 群组 ID). Set `space = group`:

```console
[mygroup]
type = yun139
authorization = ...
space = group
group_id = 12345678901234567
```

As with `family_id`, exactly one group is auto-discovered; several are refused
with the id and name of every group the account belongs to, so leaving
`group_id` out is also the quickest way to list them:

```console
$ rclone lsf mygroup:
Failed to create file system for "mygroup:": yun139: account belongs to 2 shared groups: 12345678901234567 (f), 12345678901234568 (photos); set --yun139-group-id to the one you want
```

Note that a family cloud and a shared group are not interchangeable: sending a
group id to the family API (or the other way round) is answered by the server
as `1809112500: 系统内部错误`, not as "wrong space".

Supported in a shared group: listing and walking, reading files, `rclone link`
(links are minted for 24 h and take no expiry parameter, like the family
cloud), `mkdir`, `rmdir`, `purge`, rename, delete and uploads. Deletes go to the
group recycle bin: the PC client can list and restore it, but rclone has no API
for it, so a deletion is only recoverable by hand in the client or by
re-uploading from the source, and `hard_delete` does not apply here. Uploads were verified byte-for-byte on a real
group on 2026-10-19: a 4 MiB single-part file and a 12 MiB file planned as
three 5 MiB parts both round-trip through a group download link with identical
md5 and `cmp`. The group listing carries no hash, but the storage edge does:
rclone fetches a group object's server-computed SHA-256 with a one-byte ranged
GET against its download link, so `--checksum` and `rclone check` work here too.
The probe costs one link mint plus one request per object, and an object whose
probe fails is compared by size rather than reported as corrupt.

Server-side `move`, `dirmove` and `copy` work in a group (verified against a
live group on 2026-10-20).

* `move` uses the group's own batch task (`createBatchOprTask`,
  `eventType: "move"`), which the family space does not have. Moving a file into
  the directory it already lives in is issued as a rename instead, because the
  task refuses it.
* `dirmove` moves the whole subtree in one task. A directory whose new home is
  its current parent is renamed - the task answers result code 3 for that, and
  `modifyGroupContent` with the `catalog` type does the job.
* `copy` has no server-side copy task. It is offered as a rapid upload: the
  source's SHA-256 is sent to the create endpoint declared as a single part, and
  when the store already holds that content it mints the new entry without any
  bytes moving. The store matches on hash and size, not on the part layout the
  content arrived in: a 13 MiB file uploaded as three 5 MiB parts copied this
  way. Anything the store declines - content it does not hold, a destination
  name that is taken, a request it refuses with `02010501` - is declined rather
  than failed, so rclone copies it by moving bytes instead.

`root_folder_id` is not accepted with `space = group`, because a group entry is
addressed by its id *and* the server path learned from its parent listing.

`rclone about` on a group or family remote reports the **account-wide** quota:
both shared spaces draw on the same pool as the personal cloud and neither has a
quota API of its own. To measure what one space actually holds, walk it
(`rclone size grp:`) - which is also the only way to tell, before writing,
whether the data fits.

### Sharing an account with OpenList

The token is shared with OpenList. The yun139 backend refreshes the
token automatically when the cached one is within 15 days of expiry
(`minTokenLifetime`), extending its validity via the official
`authTokenRefresh` endpoint and writing the new token back to the
config file.

To avoid two programs (e.g. rclone and OpenList) both refreshing the
same account, either:

- set `no_refresh = true` on the yun139 remote when another program
  manages the token, or
- rely on the built-in in-process guard: all yun139 remotes of one
  account in a single rclone process share one token state and refresh
  under one lock, so concurrent remotes do not rotate a stale token out
  from under each other. Note this guard is per-process: a refresh
  writes the new token back to the config file, but a *separate* rclone
  process does not re-read it until it starts, so coordinating between
  separate processes still needs `no_refresh` on all but one of them.

### Token refresh & `user_domain_id`

Refresh is triggered during backend setup (`NewFs`) whenever the token
has 15 days or less left. The refresh call must send the
`<user-domain-id>`-style id (a long number, e.g. `1000000000000000001`)
as its `userId`; the server rejects the phone number with
`ERRORCODE: 05010003`.

The id is auto-discovered from the server and written back to the
`user_domain_id` config field on first use. You normally do not need to
set it manually. If a manually-configured `user_domain_id` turns out to
be wrong, the backend detects the refresh failure, re-discovers the id
and retries once, so a stale value self-heals instead of blocking.

Two boundary behaviours worth knowing:

- While the token still has more than 15 days left, no refresh happens,
  so an (unused) wrong `user_domain_id` has no effect until the token
  nears expiry.
- A refresh failure (e.g. wrong `user_domain_id` or a network error)
  aborts `NewFs`, which blocks every operation - this is why the wrong
  id is auto-corrected rather than trusted.
- Setting `no_refresh = true` skips refresh entirely: the token is used
  as-is until it expires, then operations fail. Use it only when another
  program owns the token.

### Advanced options

These options are advanced and rarely need changing. They are also
available as flags (`--yun139-<option>`).

- `root_folder_id`: ID of the root folder. Leave blank for the top level.
- `user_domain_id`: the `<user-domain-id>`-style id. Auto-discovered on
  first use, so normally you do not need to set it.
- `space`: which storage space to use — `personal` (个人云), `family`
  (家庭云) or `group` (共享群). Default `personal`. When set to `family` you
  usually also need `family_id`, and when set to `group` you usually also
  need `group_id` (see the two sections above; in both cases exactly one
  space of that kind is auto-discovered).
- `group_id`: shared group ID, required when `space` is `group` and the
  account belongs to several groups. A numeric id, e.g.
  `1234567890123456789`. A group id is not a family cloud id: sending one
  where the other belongs is answered as `1809112500: 系统内部错误`.
- `hard_delete`: when `true`, delete permanently instead of moving files
  to the recycle bin. Only applies to the personal space. Default `false`.
- `no_refresh`: never refresh the token. Use when another program owns
  the token (see "Sharing an account with OpenList" above).
- `region_code`: the upload CDN scheduling node code, format
  `province:city`, e.g. `531:543` (江苏无锡). The official PC client
  sends it with `/file/create`; set it and personal-space uploads also
  carry a `userRegion` so the server schedules a nearby upload CDN,
  which can noticeably affect node choice and throughput. Leave blank to
  omit. Default empty.
- `disable_http2`: disable HTTP/2 for all yun139 traffic. HTTP/2
  multiplexes every concurrent part upload onto one TCP connection,
  capping total upload throughput at a single connection's bandwidth; set
  this to use HTTP/1.1 keep-alive instead so concurrent part uploads
  spread across multiple parallel TCP connections. Default `false`.
- `part_size`: part size for uploads (default 5 MiB). Must be a multiple
  of 64 bytes; the server rejects parts smaller than 5 MiB. Larger parts
  mean fewer upload requests per file.
- `upload_concurrency`: how many parts of a single file are PUT in
  parallel (default 4). A higher value speeds up large-file uploads at
  the cost of more concurrent connections.
- `max_file_size`: override the automatically-detected single-file upload
  limit. `0` (default) auto-detects the account's member tier and applies
  its limit (no-member 5G / silver 8G / gold 20G / diamond 500G); files
  larger than the limit are skipped client-side with a `NoRetryError`. Set
  a non-zero value to force a specific cap regardless of the detected tier.
  Ignored when `no_member_check` is set.
- `no_member_check`: when `true`, skip the member-tier probe and the
  client-side single-file size guard entirely, uploading files of any
  size and letting the server reject an oversized file (`04010319 权益不足`)
  instead. Default `false`.
- `encoding`: the character encoding applied to file names (see the
  [encoding section in the overview](/overview/#encoding)).

Uploads of files larger than `part_size` split the file into parts and
PUT them concurrently (bounded by `--yun139-upload-concurrency`). Copies
driven by the multi-thread engine (`--multi-thread-streams > 1`, files
above `--multi-thread-cutoff`) stage their chunks in parallel and then
run the same multi-part pipeline, so both paths respect
`--yun139-upload-concurrency`.

### Public links

`rclone link` returns a direct download link for a single file:

```console
rclone link yun139:path/to/file.bin
```

`rclone link` mints the URL fresh (it does not reuse the download-URL cache, so
the holder gets the full lifetime the server grants). `--expire` reaches the
personal cloud as the request's `expireSec` (the default is the 86400s the
official client asks for); the family cloud has no expiry parameter, so
`--expire` is ignored there with a warning.

The server fixes the granted lifetime per space:

- personal cloud (`/hcy/file/getDownloadUrl`): **15 minutes**, whatever
  `expireSec` asks for.
- family cloud (`getFileDownLoadURLV2`): **24 hours**.

Measured 2026-10-01 on a personal account (206 at five minutes, 403 at fifteen;
the URL carries `X-Amz-Expires=900` and is byte-identical for `expireSec` 3600,
21600 and 86400), and confirmed by the official client's own capture of
2026-09-03, where a `expireSec: 86400` request comes back with `expiration` set
to the issue time plus 15 minutes.

`--unlink` is meaningless: the URL is a direct download link, not a stored share
that can be revoked. Directories cannot be linked: `rclone link` returns
`fs.ErrorCantShareDirectories`.

### Limitations

- The single-file upload size is capped by the account's member tier
  (no-member 5G / silver 8G / gold 20G / diamond 500G). By default the
  backend probes the tier and skips oversized files client-side; the
  server also rejects an over-limit file at `create` time with
  `04010319: 权益不足`. Set `--yun139-no-member-check` to disable the
  client-side guard and let the server enforce the limit.
- Download URLs are fetched per object and cached for well under the lifetime
  the server grants, which is per space: 15 minutes on the personal cloud
  (whatever `expireSec` asks for) and 24 hours on the family cloud - see
  [Public links](#public-links). A stream that outlives the cache window simply
  refetches the link (the personal cloud's expired links answer 403, which
  `Open` already retries).
- The family cloud's rename / move API requires the server-side path
  (`root:/x/y`) of every involved directory. rclone learns these paths
  incrementally as it lists parents; a Move against a never-listed
  directory may need a List of the parent first.
- The family cloud's rename appends the renamed entry's own extension
  to a requested name that does not already end with it, and its reply
  reports the name it actually stored: renaming `movie.mkv` to `plain`
  stores `plain.mkv`, and renaming it to `other.mp4` stores
  `other.mp4.mkv`. rclone treats a stored name other than the requested
  one as a failed rename, so a family Move onto a free name without the
  right extension reports an error instead of leaving the file under a
  name you did not ask for. Uploads are not affected (the server stores
  the requested name verbatim), and the personal cloud never appends.
- The chunked copy engine (`OpenChunkWriter`) stages chunks into a temp
  file at their part offsets and runs the normal upload pipeline on
  `Close` (139 needs the whole-file SHA-256 before it hands out part
  upload URLs, so the parts cannot be streamed directly). Concurrency
  within a file is controlled by `--yun139-upload-concurrency`.
- 139 does not expose a per-folder total size; folder size always
  shows 0.
- 139 does not allow `SetModTime` after upload; the field always
  reports `ErrorCantSetModTime`. The server stamps its own clock on
  every upload and ignores the modification time the caller supplies,
  so a file's cloud timestamp is its upload time. Because that
  timestamp can never be made to match the local one, `Precision`
  reports `ModTimes not supported` and rclone compares on
  size: a file whose size is unchanged is not re-uploaded. Without
  that, rclone sees the mtime mismatch, cannot correct it without
  re-uploading, and rewrites every file on every `sync`. Use
  `--checksum` when you need content comparison rather than size (the
  personal cloud carries SHA-256 in its listing; the shared group answers
  it per object with a one-byte ranged GET; the family cloud exposes no
  hash, so `--checksum` degrades to size there).
- The `fstests` integration suite is not expected to pass on this
  backend, and its failures do not indicate a regression. The one
  failure is `FsDirMove`: the suite calls the backend's `DirMove`
  directly, and this backend deliberately returns `ErrorCantDirMove`
  because the 139 API refuses a directory-level move
  (`04000002: 请求参数不合法`). `rclone move`/`moveto` of a directory
  still works: the engine sees `ErrorCantDirMove` and moves the files
  one by one, then removes the source directories. Run the suite
  against a pristine checkout of the parent commit to confirm a
  failure predates your change before investigating it.
  With `space = group` the suite was measured clean (90 PASS / 34 SKIP /
  0 FAIL, 2026-10-19, confined to a dedicated sub-directory): the group
  clears `Move`/`Copy`/`DirMove` from its features, so those subtests skip
  instead of failing on the deliberate refusal.
- 139 cannot store empty (0-byte) files: `Put`/`Update`/`OpenChunkWriter`
  refuse them with `ErrorCantUploadEmptyFiles`, and files of unknown
  size are rejected up front.
- `Update` is lossless: the existing file is renamed to a backup name
  (`<name>-rclone-old-XXXXXXXX<ext>`, keeping the leaf's extension so the
  family cloud does not append it again) before the new content is
  uploaded, and is renamed back if the upload fails. A crash between the
  two steps leaves the old content under that backup name; the next
  successful upload of the same file removes it. Names matching that
  shape are reserved for this use.
- A reply that does not say which name the server stored an entry under
  (some server builds omit the field) is resolved by looking the entry up
  by id, rather than assuming the requested name. A rename the server
  stored under a suffixed name is reported as a failure in either case,
  so rclone never addresses a path the server does not hold.
- A part PUT that fails with a retryable transport error, `408`, `429`,
  a `5xx`, or a `400` carrying
  `RequestTimeout`/`SlowDown`/`InternalError`/`IncompleteBody` is retried
  on the same pre-signed URL up to `--low-level-retries` times. A
  `Retry-After` response is honoured up to 30s, including the
  command-level retry. `--timeout` remains the transport's
  response-header timeout and does not bound the upload body, so a slow
  but progressing part is not killed. An error response body is read
  with a 5s deadline, so a stalled error page cannot hold the loop.
  When the attempts are exhausted the error is marked as a low-level
  no-retry: the copy engine does not re-upload the whole file, and
  `--retries` decides whether the sync runs again. `401`, `403`, `404`,
  `409`, `410`, `3xx`, a `400` carrying
  `RequestExpired`/`ExpiredToken`/`AuthorizationQueryParametersError`,
  and a missing, empty or malformed upload URL are not replayed on the
  same URL but still allow the command-level retry; other `4xx` replies
  are permanent and stop both ladders, unless another file in the same
  run produced a retryable error. `create` and `complete` are still
  single calls; `getUploadUrl` still runs through the pacer, whose retry
  count is the same `--low-level-retries`.
  The flag also bounds the download engine's chunk reopens and its
  whole-file retry, so on unreliable links use a small value. A part
  error that exhausts its retries exits with code 6 (`NoRetryError`)
  rather than 5. Worst case for one file is roughly
  `attempts x (upload time + backoff + Retry-After)` per command run;
  `--low-level-retries 2 --retries 1` fails fast and leaves the re-run
  to a fresh trigger.
- Business errors carry a typed `apiError {code,message}` and are never
  retried. In particular the member-quota rejection
  `04010319: 权益不足` is wrapped in `NoRetryError` so `copy`/`sync`
  do not resend the whole file.
- A shared group refuses directory names carrying one of its blocked words
  (`1909011520 敏感词校验失败`), and it refuses them again for every file
  below. Each such upload logs `SKIP <parent>/: ...` naming the object's own
  parent directory, which a caller can turn into an exclude covering exactly
  the files the group will never accept, and the error is marked as not
  retryable. A file sitting at the remote root logs no line: naming `.` would
  exclude the entire remote.
- The personal space is case-insensitive and supports empty directories.
  The family space exposes no hashes, so family comparisons fall back to
  size + modtime.
- A `/file/create` call returns upload URLs for at most 100 parts at a
  time; parts beyond that are fetched through `/file/getUploadUrl` in
  batches, all transparently.
- 139 enforces Windows filename rules and rejects names containing the
  reserved ASCII characters `" * : < > ? \ |` with
  `04000002: 文件名称不符合标准` (control characters are rejected too).
  The default encoding escapes all eight to the encoder's fullwidth
  substitutes, which the server stores verbatim, so such names work
  normally and survive a round trip. Configuring `encoding` without the
  flags covering them makes the backend refuse the name client-side
  with `NoRetryError` rather than pushing it to the server. CJK,
  accented Latin (é), BMP symbols (© ® ° ± ✓) and non-BMP emoji are
  all accepted. Note that rclone itself turns `\` into a path separator
  in a remote path on Windows before the backend sees it, so a
  backslash can only reach the server through the API.
