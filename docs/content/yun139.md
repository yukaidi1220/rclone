# Yun139

[Yun139](https://yun.139.com) is the personal cloud storage service offered by
China Mobile (中国移动), also marketed as "MCloud" or "和彩云". It offers a
personal (个人云) and a family (家庭云) space with web, mobile and PC clients.

Rclone accesses Yun139 through the same "personal_new" and family
orchestration APIs used by
[OpenList](https://github.com/OpenListTeam/OpenList). You need an
authorization token to configure the backend.

## Configuration

Run `rclone config` and follow the interactive setup; the backend
appears as `yun139` in the storage-type menu. The only required option
is the authorization token; the rest have sensible defaults.

### Obtaining an authorization token

The easiest way is to copy the `Authorization` header value from an
existing [OpenList](https://github.com/OpenListTeam/OpenList) 139 storage
config — the field is already a `Basic ` + base64 string.

Alternatively, log in to <https://yun.139.com> in a browser, open the
network panel, look for any request to `*.yun.139.com` and copy the
value of the `Authorization` request header. The value starts with
`Basic ` followed by the base64 of
`pc:<phone-number>:<token>|...|<expiry-millis>`.

### SHA-256 rapid upload (秒传)

Rclone masquerades as the official 139 PC client on every request to
the personal cloud. This is required for the server to honour the
`sha256` field in `/file/create` and short-circuit the upload to a
hash match (秒传). The masquerade is automatic and not
user-configurable.

### Family cloud (新家庭云)

The family cloud uses a different base host and a `family_id` (also
called "cloudID" or "群组 ID" in the 139 client). When your account has
exactly one family cloud the backend auto-discovers the id for you; if
you belong to several, you must set `family_id` to choose one — the
backend refuses to guess rather than pick the wrong group.

To find your `family_id`:

1. Open the 139 PC client and sign in
2. Click "我的家" (My Family) in the sidebar - the URL in the
   browser bar contains the id, e.g. `https://yun.139.com/family/12345678901234567`
3. Copy the trailing number

Then configure the backend:

```console
[myfamily]
type = yun139
authorization = ...
space = family
family_id = 12345678901234567
```

Without `family_id` the first family endpoint call returns
`1010220314: 家庭云不存在` - this is the live server's response, not a
backend bug. If the user account has not joined or created a family
group the family API has nothing to talk to.

### Sharing an account with OpenList

The token is shared with OpenList. The yun139 backend refreshes the
token automatically when the cached one is within 15 days of expiry
(`minTokenLifetime`), extending its validity via the official
`authTokenRefresh` endpoint and writing the new token back to the
config file.

To avoid two programs (e.g. rclone and OpenList) both refreshing the
same account, either:

- set `no_refresh = true` on the yun139 remote when another program
  manages the token, or
- rely on the built-in in-process guard: all yun139 remotes of one
  account in a single rclone process share one token state and refresh
  under one lock, so concurrent remotes do not rotate a stale token out
  from under each other. Note this guard is per-process: a refresh
  writes the new token back to the config file, but a *separate* rclone
  process does not re-read it until it starts, so coordinating between
  separate processes still needs `no_refresh` on all but one of them.

### Token refresh & `user_domain_id`

Refresh is triggered during backend setup (`NewFs`) whenever the token
has 15 days or less left. The refresh call must send the
`<user-domain-id>`-style id (a long number, e.g. `1301956522699563527`)
as its `userId`; the server rejects the phone number with
`ERRORCODE: 05010003`.

The id is auto-discovered from the server and written back to the
`user_domain_id` config field on first use. You normally do not need to
set it manually. If a manually-configured `user_domain_id` turns out to
be wrong, the backend detects the refresh failure, re-discovers the id
and retries once, so a stale value self-heals instead of blocking.

Two boundary behaviours worth knowing:

- While the token still has more than 15 days left, no refresh happens,
  so an (unused) wrong `user_domain_id` has no effect until the token
  nears expiry.
- A refresh failure (e.g. wrong `user_domain_id` or a network error)
  aborts `NewFs`, which blocks every operation - this is why the wrong
  id is auto-corrected rather than trusted.
- Setting `no_refresh = true` skips refresh entirely: the token is used
  as-is until it expires, then operations fail. Use it only when another
  program owns the token.

### Advanced options

These options are advanced and rarely need changing. They are also
available as flags (`--yun139-<option>`).

- `root_folder_id`: ID of the root folder. Leave blank for the top level.
- `user_domain_id`: the `<user-domain-id>`-style id. Auto-discovered on
  first use, so normally you do not need to set it.
- `space`: which storage space to use — `personal` (个人云) or `family`
  (家庭云). Default `personal`. When set to `family` you usually also
  need `family_id` (see "Family cloud" above).
- `hard_delete`: when `true`, delete permanently instead of moving files
  to the recycle bin. Only applies to the personal space. Default `false`.
- `no_refresh`: never refresh the token. Use when another program owns
  the token (see "Sharing an account with OpenList" above).
- `region_code`: the upload CDN scheduling node code, format
  `province:city`, e.g. `531:543` (江苏无锡). The official PC client
  sends it with `/file/create`; set it and personal-space uploads also
  carry a `userRegion` so the server schedules a nearby upload CDN,
  which can noticeably affect node choice and throughput. Leave blank to
  omit. Default empty.
- `disable_http2`: disable HTTP/2 for all yun139 traffic. HTTP/2
  multiplexes every concurrent part upload onto one TCP connection,
  capping total upload throughput at a single connection's bandwidth; set
  this to use HTTP/1.1 keep-alive instead so concurrent part uploads
  spread across multiple parallel TCP connections. Default `false`.
- `part_size`: part size for uploads (default 5 MiB). Must be a multiple
  of 64 bytes; the server rejects parts smaller than 5 MiB. Larger parts
  mean fewer upload requests per file.
- `upload_concurrency`: how many parts of a single file are PUT in
  parallel (default 4). A higher value speeds up large-file uploads at
  the cost of more concurrent connections.
- `max_file_size`: override the automatically-detected single-file upload
  limit. `0` (default) auto-detects the account's member tier and applies
  its limit (no-member 5G / silver 8G / gold 20G / diamond 500G); files
  larger than the limit are skipped client-side with a `NoRetryError`. Set
  a non-zero value to force a specific cap regardless of the detected tier.
  Ignored when `no_member_check` is set.
- `no_member_check`: when `true`, skip the member-tier probe and the
  client-side single-file size guard entirely, uploading files of any
  size and letting the server reject an oversized file (`04010319 权益不足`)
  instead. Default `false`.
- `encoding`: the character encoding applied to file names (see the
  [encoding section in the overview](/overview/#encoding)).

Uploads of files larger than `part_size` split the file into parts and
PUT them concurrently (bounded by `--yun139-upload-concurrency`). Copies
driven by the multi-thread engine (`--multi-thread-streams > 1`, files
above `--multi-thread-cutoff`) stage their chunks in parallel and then
run the same multi-part pipeline, so both paths respect
`--yun139-upload-concurrency`.

### Limitations

- The single-file upload size is capped by the account's member tier
  (no-member 5G / silver 8G / gold 20G / diamond 500G). By default the
  backend probes the tier and skips oversized files client-side; the
  server also rejects an over-limit file at `create` time with
  `04010319: 权益不足`. Set `--yun139-no-member-check` to disable the
  client-side guard and let the server enforce the limit.
- The personal cloud's `/file/getDownloadUrl` URLs are time-limited
  (rclone requests `expireSec:86400`, i.e. 24h, and caches the link per
  object for up to 23h), so streaming a large file should not need more
  than one refresh per object.
- The family cloud's rename / move API requires the server-side path
  (`root:/x/y`) of every involved directory. rclone learns these paths
  incrementally as it lists parents; a Move against a never-listed
  directory may need a List of the parent first.
- The family cloud's rename appends the renamed entry's own extension
  to a requested name that does not already end with it, and its reply
  reports the name it actually stored: renaming `movie.mkv` to `plain`
  stores `plain.mkv`, and renaming it to `other.mp4` stores
  `other.mp4.mkv`. rclone treats a stored name other than the requested
  one as a failed rename, so a family Move onto a free name without the
  right extension reports an error instead of leaving the file under a
  name you did not ask for. Uploads are not affected (the server stores
  the requested name verbatim), and the personal cloud never appends.
- The chunked copy engine (`OpenChunkWriter`) stages chunks into a temp
  file at their part offsets and runs the normal upload pipeline on
  `Close` (139 needs the whole-file SHA-256 before it hands out part
  upload URLs, so the parts cannot be streamed directly). Concurrency
  within a file is controlled by `--yun139-upload-concurrency`.
- 139 does not expose a per-folder total size; folder size always
  shows 0.
- 139 does not allow `SetModTime` after upload; the field always
  reports `ErrorCantSetModTime`. Timestamp precision is 1 second.
- 139 cannot store empty (0-byte) files: `Put`/`Update`/`OpenChunkWriter`
  refuse them with `ErrorCantUploadEmptyFiles`, and files of unknown
  size are rejected up front.
- `Update` is lossless: the existing file is renamed to a backup name
  (`<name>-rclone-old-XXXXXXXX<ext>`, keeping the leaf's extension so the
  family cloud does not append it again) before the new content is
  uploaded, and is renamed back if the upload fails. A crash between the
  two steps leaves the old content under that backup name; the next
  successful upload of the same file removes it. Names matching that
  shape are reserved for this use.
- A reply that does not say which name the server stored an entry under
  (some server builds omit the field) is resolved by looking the entry up
  by id, rather than assuming the requested name. A rename the server
  stored under a suffixed name is reported as a failure in either case,
  so rclone never addresses a path the server does not hold.
- Business errors carry a typed `apiError {code,message}` and are never
  retried. In particular a part PUT whose 4xx error comes back from the
  CDN, and the member-quota rejection `04010319: 权益不足`, are wrapped
  in `NoRetryError` so `copy`/`sync` do not resend the whole file.
- The personal space is case-insensitive and supports empty directories.
  The family space exposes no hashes, so family comparisons fall back to
  size + modtime.
- A `/file/create` call returns upload URLs for at most 100 parts at a
  time; parts beyond that are fetched through `/file/getUploadUrl` in
  batches, all transparently.
- 139 enforces Windows filename rules and rejects names containing the
  reserved ASCII characters `" * : < > ? \ |` with
  `04000002: 文件名称不符合标准` (control characters are rejected too,
  but the default encoding handles those). rclone rejects these eight
  characters client-side with `NoRetryError` instead of pushing them to
  the server. CJK, accented Latin (é), BMP symbols (© ® ° ± ✓) and
  non-BMP emoji are all accepted.
